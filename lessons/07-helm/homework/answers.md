1. Chart הוא חבילת ההגדרות והתבניות של האפליקציה, ואילו Release הוא התקנה בפועל של אותה חבילה ב-Kubernetes.
בפרויקט ShopList, התיקייה helm/shoplist היא ה-Chart, וההתקנה בשם shop היא ה-Release.

2. הסרנו את namespace.yml כדי ש־Helm יוכל לנהל את ההתקנה בסביבות שונות ללא Namespace קבוע בקבצים.
במקומו משתמשים ב־--create-namespace ליצירת ה־Namespace וב־{{ .Release.Namespace }} כדי להציב את שמו בתבניות.

3. בקובץ values-big.yaml הוגדרו רק שני הערכים שרצינו לשנות: מספר העותקים של Backend ושל Stats.
שאר ההגדרות, כמו nodePort: 30080, מגיעות מקובץ ברירות המחדל values.yaml. Helm משלב את שני הקבצים בזמן העדכון.

4. האפליקציה המשיכה לעבוד בזכות מנגנון Rolling Update של Kubernetes, שמחליף Pods בהדרגה ולא מוחק את כולם בבת אחת.
מכיוון שה־Image החדש היה שבור, ה־Pods החדשים לא הצליחו לעלות, אך העותקים הישנים והתקינים של Backend המשיכו לטפל בבקשות.

5. פעולת Rollback יוצרת Revision חדש עם ההגדרות של הגרסה הקודמת, במקום למחוק את הגרסאות שנוצרו לאחריה.
כך Helm שומר היסטוריה מלאה של ההתקנות, העדכונים והשחזורים, ומאפשר לעקוב אחר כל שינוי שבוצע במערכת.

6. ללא ההגדרה helm.sh/resource-policy: keep, פעולת helm uninstall הייתה מוחקת גם את ה־PVC של PostgreSQL.
כתוצאה מכך, שלושת המוצרים היו עלולים להימחק, ולא להופיע לאחר ההתקנה מחדש. ההגדרה keep שומרת את ה־PVC גם לאחר הסרת ה־Release.

7. Helm לא מצא את הערך backend.replica בגלל טעות בשם המשתנה, ולכן הפיק שורת replicas ריקה. כתוצאה מכך, Kubernetes עשוי להפעיל עותק אחד כברירת מחדל במקום שלושה.
ניתן לגלות את הטעות באמצעות helm template, שמציג את קובצי ה־YAML לאחר החלפת המשתנים בערכים.
